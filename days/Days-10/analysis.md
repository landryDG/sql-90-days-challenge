# 📅 DAY 10 — Analyse & raisonnement

---

# 🎯 Objectif

Comprendre qu'une analyse ne commence pas directement par une requête SQL.

Avant de chercher une réponse dans les données, je dois comprendre la question métier, identifier les informations disponibles et construire progressivement mon raisonnement.

---

# 🧠 Ce que j'ai appris

J'ai compris qu'une question métier ne donne pas toujours directement les indicateurs à analyser.

Par exemple, si un responsable me demande :

> Quelles sont les régions qui méritent une attention particulière ?

Je dois d'abord essayer de comprendre ce qu'il entend par « mérite une attention particulière ».

Cela peut concerner :

- une baisse du chiffre d'affaires ;
- une baisse des ventes ;
- une diminution du nombre de clients ;
- un temps de traitement trop élevé.

Si la demande est trop vague, je peux chercher à obtenir plus de précisions.

Si aucun critère précis n'est défini, je peux construire une première approche à partir du contexte de l'entreprise et des données disponibles.

---

# 🔍 Ce que cela peut concerner

Selon la problématique, je peux analyser différents indicateurs.

Dans le cas des données utilisées pendant cette formation, je peux notamment m'intéresser à :

- la région ;
- le chiffre d'affaires ;
- le nombre de ventes ;
- le nombre de clients ;
- le nombre de demandes ;
- le temps de traitement.

Ces indicateurs me permettent de construire une première vue d'ensemble et de rechercher des écarts entre les différentes régions.

---

# 📊 Ma démarche analytique

La démarche que je retiens est la suivante :

**Question métier**

↓

**Identifier les indicateurs pertinents**

↓

**Construire une vue d'ensemble**

↓

**Chercher un signal, un écart ou une anomalie**

↓

**Zoomer sur les données**

↓

**Formuler une hypothèse**

↓

**Vérifier cette hypothèse**

↓

**Réorienter l'analyse si les données ne soutiennent pas l'hypothèse**

↓

**Conclure**

↓

**Proposer une recommandation si nécessaire**

J'ai compris qu'une hypothèse n'est pas quelque chose que je dois absolument prouver.

Elle représente une piste que je dois tester avec les données.

---

# 💡 Ce que je retiens

Le SQL est un outil qui permet d'explorer les données, mais une analyse commence avant l'écriture de la requête.

Je dois d'abord comprendre ce que je cherche, choisir les indicateurs pertinents et observer les données dans leur ensemble.

La logique que je retiens est :

> **Vue d'aigle → signal → zoom → hypothèse → vérification → conclusion**

Si ma première hypothèse n'est pas soutenue par les données, je dois être capable de réorienter mon analyse.

L'objectif n'est pas de prouver que mon hypothèse est correcte, mais de comprendre ce que les données permettent réellement de conclure.
